# КЭМС Расписание

Android-приложение для просмотра расписания занятий, отслеживания изменений и получения напоминаний о предстоящих занятиях.

Проект собран вокруг идеи «расписание как живой экран»: приложение получает календарь в формате iCalendar (`.ics`), разбирает занятия, сохраняет их локально, сравнивает обновления с предыдущей версией расписания и отображает результат в современном интерфейсе Jetpack Compose.

> **Текущее состояние:** документация описывает состояние ветки `Chat-gpt` на 28 сентября 2026 года. Сборка проекта в рамках подготовки этого README не запускалась — проверка сборки и запуск приложения остаются за разработчиком.

## О приложении

**КЭМС Расписание** — нативное Android-приложение с интерфейсом на Jetpack Compose.

Приложение рассчитано на сценарий, в котором расписание публикуется как календарь iCalendar. Пользователь выбирает группу или указывает собственную ссылку на `.ics`, после чего приложение:

1. загружает календарь по HTTP(S);
2. разбирает `VEVENT`;
3. преобразует записи календаря в доменные `ClassEvent`;
4. сохраняет расписание в Room;
5. сравнивает новое состояние с предыдущим;
6. фиксирует изменения в журнале;
7. планирует локальные напоминания;
8. отображает расписание по дням.

Основной пакет исходного кода — `com.example`.

Название приложения в ресурсах Android — **«КЭМС Расписание»**.

## Основные возможности

### Расписание

- просмотр занятий по дням;
- отображение времени начала и окончания;
- определение текущего занятия;
- отображение ближайшего занятия;
- визуальное различие предстоящих, текущих, завершённых и отменённых занятий;
- отображение преподавателя;
- отображение аудитории;
- отображение типа занятия;
- отображение информации о подгруппах;
- поддержка онлайн-занятий и извлечение Zoom-ссылки/идентификатора/пароля из данных события;
- карточки занятий с анимациями и интерактивным состоянием нажатия;
- подробная информация о занятии в отдельном интерфейсном слое.

### Работа с расписанием

- загрузка iCalendar по URL;
- поддержка стандартных `VEVENT`;
- разворачивание folded iCalendar-строк;
- обработка `TZID`;
- обработка UTC-времени с суффиксом `Z`;
- обработка локального времени;
- обработка событий без `DTEND` с продолжительностью по умолчанию;
- распознавание отменённых занятий;
- извлечение преподавателя из `DESCRIPTION` и `SUMMARY`;
- сохранение расписания локально.

Приложение хранит историю изменений расписания и различает:

- перенос времени;
- смену аудитории;

- отмену;

## Архитектура

Проект не использует тяжёлый DI-фреймворк. Основные зависимости создаются на уровне приложения и репозитория.

### Слой приложения

`PlanovoApp` — Android `Application`.

Он создаёт:

- `NotificationHelper`;
- `ScheduleRepository`.

`MainActivity` устанавливает Compose-контент и получает `ScheduleViewModel`.

### Слой UI

Основные экраны:

- `ScheduleScreen`;
- `ProfileScreen`;
- `NotesScreen`;
- `PassesScreen`.

Состояние основного интерфейса управляется через `ScheduleViewModel`.

Compose использует `collectAsStateWithLifecycle()`, поэтому состояние ViewModel привязано к жизненному циклу Android.

### Слой данных

Основной фасад — `ScheduleRepository`.

Он отвечает за:

- текущую группу;
- сохранённые группы;
- настройки;
- загрузку расписания;
- работу с локальной БД;
- вычисление/сохранение изменений;
- уведомления;
- заметки;
- пропуски;
- тему;
- формат времени.

### Локальное хранилище

Используется Room.

Основные сущности:

- `ScheduleEntity`;
- `ChangeEntity`.

DAO — `ScheduleDao`.

### Удалённые данные

`CalendarRemoteDataSource` использует OkHttp для загрузки `.ics`.

Отдельный `IcsParser` преобразует iCalendar в доменные модели.

## Модель данных

### `ClassEvent`

Главная доменная модель занятия.

Содержит:

| Поле | Назначение |
|---|---|
| `id` | стабильный идентификатор события |
| `title` | название занятия |
| `description` | описание |
| `teacher` | преподаватель |
| `location` | аудитория/место |
| `lessonType` | тип занятия |
| `startTimeMillis` | начало |
| `endTimeMillis` | окончание |
| `isCancelled` | отменено ли занятие |
| `hasChanges` | есть ли изменения |
| `changeDetails` | описание изменения |
| `rawSummary` | исходное название события |
| `subgroups` | явные данные подгрупп |

Модель также вычисляет:

- текущий статус;
- длительность;
- процент выполнения;
- оставшееся время;
- время до начала;
- отображаемый тип занятия;
- признак онлайн-занятия;
- Zoom URL;
- Zoom ID;
- пароль конференции;
- отображаемые подгруппы.

### Статусы

`ClassStatus`:

```text
ONGOING
UPCOMING_SOON
SCHEDULED
COMPLETED
CANCELLED
```

Занятие считается `UPCOMING_SOON`, если до начала не больше двух часов.

### Типы изменений

`ChangeType`:

```text
TIME_CHANGED
LOCATION_CHANGED
DETAILS_CHANGED
CANCELLED
NEW_CLASS
RESTORED
```

## Получение и разбор расписания

### Источник

Стандартный URL группы строится по шаблону:

```text
https://planovo.pro/api/v1/public/groups/{groupId}/calendar.ics
```

В репозитории также поддерживается пользовательский URL календаря.

### HTTP

`CalendarRemoteDataSource` использует OkHttp.

Настроены:

- timeout подключения — 15 секунд;
- timeout чтения — 20 секунд;
- автоматические redirect;
- User-Agent приложения;
- Accept для iCalendar/text/plain.

После ответа проверяется:

1. HTTP-код;
2. наличие тела;
3. наличие `BEGIN:VCALENDAR`.

Если ответ не похож на iCalendar, возвращается ошибка.

### Парсер iCalendar

`IcsParser` поддерживает:

- `UID`;
- `SUMMARY`;
- `DESCRIPTION`;
- `LOCATION`;
- `URL`;
- `STATUS`;
- `DTSTART`;
- `DTEND`;
- `TZID`;
- UTC через `Z`;
- date-only значения;
- folded lines;
- стандартные iCalendar escape-последовательности.

Также выполняется эвристическое извлечение преподавателя.

Например:

```text
SUMMARY:Математика (Иванов И.И.)
```

может быть преобразовано в:

```text
title   = Математика
teacher = Иванов И.И.
```

Аналогично обрабатываются варианты с разделителем ` - `.

## Определение изменений

Для отслеживания изменений используется `ScheduleDiff`.

Концептуально сравниваются две версии:

```text
старое расписание
        │
        ├── событие исчезло
        ├── событие появилось
        ├── изменилось время
        ├── изменилась аудитория
        └── изменились дополнительные данные
        │
        ▼
новое расписание
```

Результатом становятся `ScheduleChange`, которые сохраняются как `ChangeEntity`.

Обновление расписания в DAO выполняется транзакционно через:

```kotlin
updateScheduleWithDiff(
    newEntities = ...,
    newChanges = ...
)
```

Внутри транзакции:

1. очищаются текущие события;
2. вставляется новая версия;
3. добавляются обнаруженные изменения.

Это уменьшает вероятность увидеть частично обновлённое расписание.

## Группы

Для группы используется `SavedGroup`.

Группа содержит как минимум:

- ID;
- название;
- URL календаря.

Дополнительно сохраняется статистика и время обновления.

### Стандартная группа

В коде предусмотрена группа по умолчанию:

```text
ID: 41
Название: 2423 УИР · 3 курс
```

При отсутствии новой конфигурации приложение умеет мигрировать старые одиночные настройки в список сохранённых групп.

### Переключение

Активная группа хранится отдельно. При переключении обновляются legacy-настройки репозитория, чтобы старые участки кода продолжали получать актуальный ID/URL.

## Уведомления

### Разрешения

Manifest содержит:

- `POST_NOTIFICATIONS`;
- `VIBRATE`;
- `RECEIVE_BOOT_COMPLETED`;
- `SCHEDULE_EXACT_ALARM`.

### Планирование

`NotificationScheduler` создаёт AlarmManager-события для будущих занятий.

При планировании учитываются ограничения:

- отменённые занятия не планируются;
- прошедший trigger time не отправляется в AlarmManager;
- события слишком далеко в будущем не планируются в текущем окне;
- существующий alarm сначала может быть отменён и создан заново.

Для API с поддержкой `setExactAndAllowWhileIdle()` используется точный alarm.

Если Android не позволяет установить exact alarm, предусмотрен fallback на обычный `set()`.

### После перезагрузки

`BootReceiver` получает `BOOT_COMPLETED` и запускает восстановление будущих уведомлений через репозиторий.

### Нажатие на уведомление

Уведомление запускает приложение и передаёт:

```text
selected_event_id
```

Это позволяет открыть/выделить нужное занятие после перехода из notification.

## Интерфейс

### Основной экран

`ScheduleScreen` отвечает за:

- выбор дня;
- список занятий;
- состояния загрузки;
- ошибки;
- обновление;
- навигацию;
- отображение групп;
- взаимодействие с ViewModel.

### Карточка занятия

`ClassCard` — основной визуальный компонент расписания.

В ней реализованы:

- статусная раскраска;
- время;
- преподаватель;
- аудитория;
- тип занятия;
- состояние текущего занятия;
- progress;
- press-анимация;
- изменение формы карточки при нажатии;
- анимированные шестерёнки;
- плавное продолжение анимации при появлении карточки в LazyColumn.

Для уменьшения количества лишних рекомпозиций live-время карточки обновляется с интервалом 5 секунд, а не каждую секунду.

### Подгруппы

`SubgroupClassCard` используется, когда одно занятие содержит несколько параллельных вариантов.

Для каждой подгруппы можно показать:

- преподавателя;
- аудиторию;
- время.

Таким образом несколько параллельных занятий визуально объединяются в один блок, но информация отдельных преподавателей и аудиторий не теряется.

### Подробности занятия

`ClassDetailDialog` используется для просмотра расширенной информации.

### Навигация

В проекте есть отдельный выразительный компонент:

`ExpressiveBottomBar`.

Он используется вместе с современным Material 3 оформлением и адаптивной навигацией.

### Темизация

Тема находится в:

## Важные детали реализации

### Локальное кеширование

Расписание не является исключительно сетевым экраном.

Room используется как локальный источник структурированных данных, поэтому архитектура позволяет отделить:

```text
сеть → синхронизация → локальное состояние → UI
```

Это особенно важно для расписания, потому что UI не должен зависеть от того, завершился ли сетевой запрос прямо сейчас.

### Сравнение по идентификаторам событий

iCalendar `UID` используется как основной идентификатор события.

Если `UID` отсутствует, парсер создаёт fallback ID на основе времени начала и хеша названия.

### Часовые пояса

Парсер не предполагает, что все даты находятся в локальном часовом поясе устройства.

Поддерживаются:

- `TZID=...`;
- UTC;
- fallback на timezone календаря;
- fallback на timezone устройства.

### Отмена

Событие считается отменённым не только при:

```text
STATUS:CANCELLED
```

но и при наличии признака отмены в названии или описании.

### Подгруппы

Модель поддерживает два варианта:

1. явный список `subgroups`;
2. эвристическое извлечение информации из описания/преподавателя.

Это позволяет не зависеть от одного строго заданного формата внешнего календаря.

### Производительность Compose

В проекте используются несколько приёмов для уменьшения лишних обновлений:

- lifecycle-aware collection;
- локальное кеширование вычисляемых подгрупп;
- обновление времени карточек раз в 5 секунд;
- `LazyColumn`;
- стабильные ключи для элементов списков;
- анимации через Compose Animation API;
- ограничение записи статистики группы, если значение не изменилось.

## Известные ограничения

1. **Сборка не запускалась во время подготовки этого README.** Документация составлена по исходному коду и Gradle-конфигурации ветки `Chat-gpt`.
2. **Формат внешнего календаря определяет качество автоматического извлечения данных.** Преподаватели и подгруппы извлекаются эвристически, поэтому нестандартный формат `.ics` может потребовать дополнительной обработки.
3. **Exact alarms зависят от ограничений Android.** Приложение пытается использовать точные alarm'ы и имеет fallback, но поведение зависит от версии Android и разрешений пользователя.
4. **Firebase-конфигурация не обязательна для чтения исходников.** В Gradle предусмотрен сценарий отсутствующего `google-services.json`, однако конкретные Firebase-возможности требуют соответствующей конфигурации.
5. **Release signing требует локальных секретов.** Они намеренно не являются частью репозитория.
6. **UI содержит большое количество анимаций.** При дальнейшей разработке важно сохранять контроль над количеством одновременно активных Compose-анимаций и частотой обновления состояния.
